# Project 3 Discussion answers

1) What are the tradeoffs between fixed and varying initial sequence numbers? How could delayed segments from an earlier connection interfere with a new instance of the same tuple?
    - This implementation uses a fixed initial sequence number of 0 at both endpoints. That keeps the sequence arithmetic simple and deterministic; the 1,024-byte transfer cap also ensures sequence numbers do not wrap. The tradeoff is that a delayed segment from an old connection can have sequence and acknowledgment numbers that look valid after the same address-and-port tuple is reused. 
    - For example, an old data segment could be mistaken for new data, or an old ACK could affect the new sender state. Varying the initial sequence number for each connection makes those collisions less likely, but requires sequence-number wraparound handling.
    - unpredictable values also make it harder for hackers to guess the sequence number and ack.
    
2) For the required 128-byte receive buffer, how does the advertised window change as data arrives and the application consumes it? What determines a useful buffer size if the fixed limit were relaxed?
    - As the 128-byte recieve buffer is filled up with data, the reciever sends out how much of the buffer is available through it's advertised window along with each ACK. This window shrinks as data arrives in-order and reaches zero when the buffer is full. When the advertised window is zero, the sender periodically probes the reciever for an update until the window opens up again. The buffer is freed when an application uses the data, which allows for the advertised window to increase and the sender can send more data.
    - If the buffer limit where relaxed then an appropriate buffer size would be determined by the sender's data arrival rate, application consumption rate, expected traffic burstiness, and update delay.
3) What happens when a data segment arrives twice because its ACK was lost? Explain how the receiver prevents duplicate delivery while helping the sender make progress.
    - The receiver accepts data only when its sequence number equals `rcvNext`. After accepting a segment, it advances `rcvNext`; if the ACK is lost and the sender retransmits that segment, its sequence number is now behind `rcvNext`, so the receiver discards it instead of delivering the bytes again. It still sends the current cumulative ACK, telling the sender which next byte is expected. The sender can then recognize the acknowledged progress and release the retained bytes.
4) Why must a receiver advertise newly available space after its application reads data? What happens if that update is lost, and how does your implementation recover?
    - Reading removes bytes from the receive buffer, increasing the advertised window. The receiver sends an ACK/window update immediately so a sender that stopped at a zero window can resume without waiting for another data segment. 
    - If that update is lost, the sender still believes the window is zero and periodically sends a non-sequenced window probe. The receiver answers with its current ACK and window; a positive update lets the sender resume. The implementation probes every 3 seconds and reports failure if it receives no valid response through the retry limit.
5) How could repeated incomplete connection handshakes exhaust your static connection table? Describe your current timeout policy and one possible improvement.
    - Each incoming SYN allocates a child connection record and leaves it in `SYN_RCVD` while the server waits for the final ACK. Repeated SYNs whose handshakes never finish can therefore occupy the bounded table and prevent legitimate connections from allocating records. The implementation retransmits the SYN-ACK every 3 seconds, up to five retries, then reports failure and frees the record. 
    - One improvement would be to use a stateless SYN cookie, so the server allocates a connection record only after receiving a valid final ACK.
6) What happens if a peer establishes a connection and remains idle indefinitely? Discuss the tradeoff between reclaiming resources and preserving a legitimate long-lived connection.
    - An established connection with no outstanding data or control segment has no active retry timer, and the implementation has no idle-connection timeout, so it remains allocated indefinitely. This preserves legitimate long-lived connections that may be quiet for an extended period, but idle peers can consumse the finite socket table and eventually block new connections. 
    - An idle timeout or optional keepalive policy could reclaim abandoned connections, but an overly aggressive timeout could incorrectly close a valid but temporarily quiet connection.
